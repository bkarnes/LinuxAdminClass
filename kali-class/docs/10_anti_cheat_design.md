# 10 — Anti-Cheat Design

## Threat model

A student wants a grade without doing the work, by:

1. **T1 — Editing an export file** (bump 3/5 → 5/5).
2. **T2 — Copying a friend's export file** wholesale.
3. **T3 — Splitting the work**: friend does exercises, ships the artifact
   files (not the export), student runs `export` on their own VM.
4. **T4 — Sharing the class secret** (everyone has it anyway).

Non-goals: preventing students from helping each other *learn* (encouraged —
that's the point of class), or defeating a student who fully simulates another
VM's machine-id *and* knows the secret *and* does the work. The goal is to
make cheating harder than doing the labs, which are short.

## Layer 1 — Document signature (defeats T1)

```
Signature = HMAC-SHA256(key = SHA256(class_secret), body)
```

- The student's runner stores only `secret_hash = SHA256(class_secret)`
  (hex string). The HMAC key is that hex string.
- The instructor recomputes the signature from the class secret and compares.
- Any single character changed anywhere in the body → mismatch.

## Layer 2 — Per-student claims (defeats T2)

For every completed exercise the export carries:

```
claim = HMAC-SHA256(secret_hash, "LinuxAdminClass-2027|<student_id>|<workshop>|<exercise>|")
```

The `student_id` is inside the message — so:

- Jane's claim for `linux-wk01:01` verifies only for `student_id=901234567`.
- If Bob submits Jane's file with his name/ID, the signature breaks (Layer 1).
- If Bob submits Jane's file *unchanged*, the header says Jane — grading
  systems keyed on student ID catch it, and the roster cross-check (Layer 3)
  catches it at the instructor's discretion.

`instructor/verify_export.py` recomputes every claim with the student_id from
the header; a file whose claims were generated by a different student fails.

## Layer 3 — VM binding (defeats T3)

- `identity.json` records `vm_uuid = /etc/machine-id` at registration.
- `kali-class whoami` writes a signed JSON (HMAC over the identity body) —
  students upload it as **Assignment 0**, building the roster:
  `student_id → vm_uuid`.
- Every export carries `VM UUID`.
- The instructor's verifier flags any export whose vm_uuid differs from the
  roster entry for that student_id.

An artifact produced on a friend's VM (T3) will carry the friend's vm_uuid in
any export that references it. Combined with Layer 2 claims (which the
artifact-owner must have generated with their own ID), the split-work attack
leaves either claims or vm_uuid inconsistent.

Additionally: `setup_vm.sh` option 2 installs rsyslog CLI logging
(`configs/bash.conf` → `/var/log/commands.log`). Every command the student
runs — including lab commands — is timestamped on *their* VM. An instructor
can ask for that log during an integrity review; a doctored export has no
matching command history behind it.

## Layer 4 — Per-student artifacts (defeats T3, Phase 2+)

For artifact-producing exercises (scripts, captures, cracked hashes, flags):

- `anti_cheat.seeded_content(student_id, workshop, exercise)` =
  `HMAC(secret_hash, class|student|workshop|exercise|seed)[:32]` —
  deterministic, unique per student per exercise.
- The runner plants seed files containing this token at workshop start
  (`ensure_seed_files`, idempotent, marked by `.kali-class-seeded`).
- Verifiers require the student's artifact to reference/contain *their* token.
- A friend's artifact contains the friend's token — useless to the copier.

First use: Week 4's backup-script lab. All cybersec weeks use it for flag
claims.

## Class secret handling (context for T4)

- Announced verbally night 1; never posted, never emailed.
- Stored only as SHA-256 on student VMs.
- Instructor keeps `instructor/shared-secret.env` (gitignored).
- If compromised mid-semester: change the secret, and have students
  `kali-class re-register` at the start of the next class (progress is kept;
  only identity re-derives).

## Residual risk (honesty section)

- Students *can* legitimately work side-by-side and both do the work — fine.
- A student who *fully understands* the scheme, knows the secret, and controls
  `/etc/machine-id` could theoretically forge everything. That student could
  also simply do the labs in less time.
- The design assumes good faith with verification, not adversarial proof.

## Test vectors (from the Phase 1 E2E test)

| Attack | Result |
|--------|--------|
| Edit progress line (T1) | ❌ Document signature MISMATCH |
| Change name/student ID (T2) | ❌ Document signature MISMATCH |
| Submit with copied claims (T2) | ❌ Claims mismatch student_id |
| Export on different VM than roster (T3) | ❌ vm_uuid MISMATCH |
